Part A · Overview

What this system is

Written for anyone following the project, not just engineers. No code in this part.

A.1Two websites, one platform

ORST and RoyalSociety are two separate, real government websites — but they are not two separate codebases. They share one content platform (WebX), the same admin tool, the same hosting stack, and the same design language, deliberately differentiated in look so the two sister institutions each feel distinct.

ORST — สำนักงานราชบัณฑิตยสภา — www.orst.go.th RoyalSociety — ราชบัณฑิตยสภา — www.royalsociety.go.th

Both are configured inside WebX as WordPress-engine tenants — one of two supported content-storage engines the platform can run a tenant on (the other is Strapi, used by other, unrelated customers on the same platform). Editors for both sites log into the same admin tool and never need to know which engine their content actually lives in.

A.2How a page reaches a visitor

The two public websites are not generated on the fly for every visitor. They are built once, ahead of time, into plain static files — the fastest and most robust way to serve a government site with predictable, infrequent content changes.

flowchart LR
  editor["Content editor"] -->|"logs in, edits a page"| studio["WebX Studio\n(admin app)"]
  studio -->|"saves content"| wp[("WordPress\n(content store)")]
  studio -->|"Rebuild now / auto after a debounce"| build["Static site build\n(Next.js)"]
  build -->|"reads content at build time"| wp
  build -->|"produces plain HTML/CSS/JS"| files["Static files"]
  visitor["Public visitor"] -->|"https://"| files

A visitor never talks to WordPress or the admin app directly — only to pre-built static files, which is why the public site stays fast and resilient even if the admin side is slow or down.

When an editor publishes a change, WebX Studio either triggers a rebuild immediately or after a short debounce window (so ten quick edits in a row don't trigger ten separate rebuilds). One exception: the breaking-news banner is fetched live by the visitor's own browser every 30 seconds, specifically so an urgent notice can go out without waiting for a full site rebuild.

A.3What an editor actually does

Every page on both sites is built from reusable content blocks — a hero banner, a card grid, a table, an event calendar — rather than free-form HTML. An editor assembles a page by choosing blocks and filling in their fields, the same mental model as PowerPoint slides.

  • Visual Builder — a live, click-to-edit preview of the actual page, for straightforward text/image changes.
  • Structured forms — for content with real fields (a job posting's title/department/deadline, an event's date/time/location), so data stays consistent and searchable rather than living inside a paragraph of text.
  • Review workflow — content can be routed through Draft → Pending → Published, with a real approval gate before anything goes live.

B.2Multi-tenant & dual-engine model

A tenant is one customer's website (ORST, RoyalSociety, and others unrelated to this delivery). Every tenant record lives in Strapi regardless of where its content lives — that record just carries an engine field saying which store to read from.

// strapi-cms/src/api/tenant/content-types/tenant/schema.json
"engine": {
  "type": "enumeration",
  "enum": ["strapi", "wordpress"],
  "default": "strapi",
  "description": "Which CmsAdapter this tenant's own content lives in. The tenant record itself always lives in Strapi regardless."
}

Both ORST and RoyalSociety are configured with engine: "wordpress". Tenant isolation inside WordPress — which has no native multi-tenancy — is enforced with a custom wtenant taxonomy applied to every content post type, checked by a general-purpose scoping guard rather than one-off checks per post type:

wordpress/mu-plugins/wtenant-taxonomy.php wordpress/mu-plugins/custom-role-enforcement.php
Why two engines, not one

Strapi-engine tenants were the platform's original design. ORST/RoyalSociety's TOR requires WordPress-family content authoring conventions and a custom WordPress theme (see B.7) — rather than fork the admin app per engine, a single CmsAdapter abstraction (B.3) lets one admin UI, one governance layer, and one set of platform-wide features (polls, breaking news, analytics) work unmodified against either engine.

B.3The CmsAdapter abstraction

Every admin operation goes through one interface, implemented once per engine. Nothing in the admin UI or its API routes branches on which engine is active — that decision is made once, at the adapter boundary.

// webx-studio/lib/cms/types.ts
export interface CmsAdapter {
  schema:  { listContentTypes(): Promise<ContentTypeInfo[]> };
  entries: { list, get, create, update, remove };
  publish: { publish, unpublish };
  media:   { upload, list, update, remove };   // tenantKey required for WordPress,
                                                 // a no-op for Strapi (self-resolved)
  auth:    { me(), listRoles(), ... };
}
webx-studio/lib/cms/types.ts webx-studio/lib/cms/strapi.ts webx-studio/lib/cms/wordpress.ts webx-studio/lib/cms/governance.ts

governance.ts sits in front of both adapters: it resolves the caller's effective tenant, enforces field-level RBAC and custom-role permissions, stamps the tenant relation on create, and routes a handful of platform-wide content types (breaking news, polls, menu items) to Strapi even for a WordPress-engine tenant's own session — those types are bookkeeping data the platform itself owns, not tenant content.

Why this needed its own registries

A new platform-wide content type must be added to three places to actually work end-to-end for a WordPress-engine tenant: strapi-cms/src/index.ts's SCOPED set (or the tenant-scoping hook silently ignores it), the seed script's public-permissions map (or its public read 403s), and governance.ts's own SCOPED/BOOKKEEPING_UIDS sets (or a WordPress-engine admin session sees an empty, uneditable panel). Found live, more than once, while building breaking-news and the nav manager.

B.4Content architecture — how a page resolves

A page's content can come from three layers, resolved in a fixed order every time public-site builds. Understanding this order is the single most important thing for anyone editing content on these two sites.

flowchart TB
  A["Static JSON fallback\ntemplates/<tenant>/content/*.json"] --> D{"WordPress page has\nits own migrated blocks?"}
  D -->|"no"| E["Use the static JSON's blocks"]
  D -->|"yes — wpPage.blocks.length > 0"| F["Use WordPress's blocks\n— WHOLESALE override, not a merge"]
  E --> G["resolveSources()\nbind any block's live-data source"]
  F --> G
  G --> H["Page-specific field overrides\n(e.g. About's derived stat counts)"]
  H --> I["Rendered static page"]

app/orst/[page]/page.tsx line ~89 — let blocks = wpPage?.blocks?.length ? wpPage.blocks : data.blocks;

The one rule that catches people every time

Once a page has been edited even once through the Visual Builder, WordPress's stored blocks field completely replaces the static JSON — not a per-block merge. Editing templates/orst/content/about.json directly has zero effect on a migrated page. This was hit repeatedly this project — a content fix landing in the repo's JSON but not on the live site — and the fix is always the same: write the correction to WordPress directly (REST API or an idempotent wordpress/seed-*.mjs script), never assume the JSON file is authoritative once a page is live.

Live-data binding: resolveSources()

Separately from the override above, an individual block can declare a source binding that pulls live WordPress data into its items array at build time — the mechanism behind event calendars, member directories, and news feeds. Ten source shapes exist (card, link, faq, mission, orgunit, document, timeline, dated, calendar, directory), each with its own mapper function:

// public-site/lib/blockSource.ts
export type BlockSource = { kind: "wp"; postType: SourcePostType; map: SourceMap; ... };

const MAPPERS: Record<SourceMap, (entries, src) => any[]> = {
  card: toCardItems, link: toLinkItems, faq: toFaqItems,
  calendar: toCalendarItems, directory: toMemberItems, /* ... */
};
A real bug this pattern already caught

toDatedItems() (RoyalSociety's activities/knowledge list rows) was the only mapper of its siblings that forgot to call fmtDateTh() on its date field — every other mapper did. The result was a raw ISO timestamp rendered straight to visitors. Fixed by matching the sibling mappers' own pattern. The lesson generalized: when one mapper in a set does something the others don't, that's usually a bug, not a design choice.

B.5Frontend design system

Both tenants share the same architecture (tokens → base → blocks → components → pages, loaded in that order) but deliberately different values, so the two sister sites read as related, not identical.

Token-driven theming, including dark mode

Every color, radius, shadow and type size is a CSS custom property — no component file contains a literal hex value. This is what makes a full dark theme possible as a pure token swap rather than a component-by-component reskin:

flowchart LR
  boot["THEME_BOOT script\n(app/layout.tsx)\nruns before first paint"] -->|"reads localStorage\nfalls back to OS preference"| attr["html[data-theme]"]
  attr -->|"light"| lightTokens[":root { --heading: teal; ... }"]
  attr -->|"dark"| darkTokens[":root[data-theme=dark] { --heading: mint; ... }"]
  lightTokens --> components["Every component references\nthe token, never a literal color"]
  darkTokens --> components
Why --heading is a separate token from --primary

--orst-primary/--rs-primary serve two genuinely different roles: filling always-dark surfaces (hero bands, solid CTA buttons — which must stay the same deep teal in either theme) and coloring heading text sitting on the page's own ground (which must flip to a light tone in dark mode). Reusing one token for both would have made dark mode's headings the same near-invisible dark teal as light mode's. Splitting the second role into --heading — a mechanical migration of ~120 plain color: declarations, leaving every background:/paired border-color: fill untouched — is what let dark mode ship as token redefinitions only, no component rewrites.

Scroll-reveal motion

A shared observer (public-site/components/ScrollReveal.tsx, mounted once for every tenant) reveals section headings and card grids as they scroll into view — with a hard safety constraint: content renders at full opacity by default regardless of whether the observer's JavaScript ever runs. Only html.js-reveal — a class added synchronously in <head>, before paint, and never at all under prefers-reduced-motion — enables the hidden-then-reveal state at all.

Cascade layers

Each tenant's stylesheets are wrapped in @layer tokens, base, blocks, components, pages (ORST) / @layer tokens, base, layout, components, accessibility, pages (RoyalSociety), matching the existing <link> load order exactly — a declared-not-implicit cascade order, verified as a zero-behavior-change refactor via before/after contrast-scan comparison.

B.6Admin platform (webx-studio)

One admin app for every tenant on the platform, regardless of engine. Notable subsystems relevant to ORST/RoyalSociety specifically:

  • Nav Manager — recursive mega-menu editor. megaMenu is a plain Strapi json field, so unlimited nesting depth needed no schema change, only a recursive editor/renderer.
  • Media Library — search/tag/reuse/caption across both engines, with real per-tenant isolation (a genuine cross-tenant leak was found and fixed during this build — see the TOR dossier, item cms-04).
  • Breaking News — the one content path that bypasses the static-rebuild pipeline entirely: the public page polls Strapi directly from the browser every 30s, the same direct-fetch pattern the live poll-vote UI uses.
  • Analytics — first-party stats always; a real GA4 Data API pull layered on top when a tenant has service-account credentials configured.
  • Responsive shell — a real hamburger/drawer below 720px, replacing what used to be a bare display:none that left a phone-width admin with no navigation at all.

B.7WordPress engine specifics

WordPress here is a pure content/REST backend — genuinely headless. wordpress/theme/webx-theme/ is real and active (satisfying the TOR's custom-theme requirement and giving wp-admin's Gutenberg editor real styling), but it renders nothing a visitor ever sees; public-site is the only rendering path.

The WordPress engine, its backups, and Keycloak all run under Compose profiles — opt-in, not started by a bare docker compose up, since not every deployment of the platform needs them.

Backups were a real, closed gap

Until this delivery, db-backup covered only Strapi's own database — the two tenants this whole contract is about had zero backup coverage, since their real content lives in wp-mysql/wp-content-data, not Strapi's Postgres. wp-db-backup closes that with the same script, rotation convention, and restore-test tooling (strapi-cms/scripts/restore-test.js) already proven against the Strapi side.

B.9Security & compliance summary

Full item-by-item verification against the TOR lives in the compliance dossier; the load-bearing measures specific to this platform's architecture:

  • PII encryption at rest — AES-256-GCM on citizen-submitted data (contact-message, registration), a dedicated key separate from Strapi's own core secrets and from webx-studio's.
  • Tenant isolation — enforced at the adapter boundary (governance.ts) for Strapi-stored data, and via the wtenant taxonomy + a general scoping guard for WordPress-stored data — not per-content-type special cases in either engine.
  • Rate limiting — a sliding-window limiter on webx-studio's own BFF routes: a tight bucket on /api/auth/*, a general one on the rest of /api/*.
  • WordPress hardening — XML-RPC disabled, version disclosure stripped, access logging with retention purge, all added where none existed before.

B.10Key architectural decisions

Static export over server rendering

A government site with infrequent content changes and a hard requirement for speed/resilience doesn't need a server rendering pages per request. output:"export" means the two live sites are files behind any web server — no runtime dependency on Node, the database, or either CMS engine being up.

One CmsAdapter interface, not one admin app per engine

Forking the admin app per engine would have meant building and maintaining governance, RBAC, and every platform-wide feature (polls, breaking news, analytics) twice. The adapter boundary keeps that logic single-sourced; only the two adapter implementations know their engine's actual API shape.

WordPress's own blocks override static JSON wholesale, not per-field

A per-field merge would need to define, for every one of ~27 block types per tenant, exactly which fields WordPress is allowed to own versus which fall back to the static file — a large surface for subtle bugs. A page is either fully static-authored or fully migrated to live editing; there is no in-between state to reason about.

Design tokens with zero literal colors in component files

This is what made a full dark theme achievable as a token-only change once the premium redesign already existed — the alternative (auditing and rewriting every component's own color declarations) would have been an order of magnitude more work and risk.
